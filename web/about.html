SECURITY & PRIVACY

Honest threat model. What this protects, and — just as important — what it does not.

How a conversation is protected

  • End-to-end encryption, post-quantum hybrid. Messages, files and calls travel directly between browsers over a WebRTC data channel. They are encrypted with AES-256-GCM using a key agreed by ECDH (P-256) + ML-KEM-768 (FIPS 203) → HKDF-SHA256 — an attacker recording traffic today cannot decrypt it even with a future quantum computer, because breaking the session requires breaking both primitives. The server only relays connection setup — it never sees keys or content.
  • Group chats are a mesh of private links. A room can hold up to six people, but there is no shared "group key": every pair of people has its own independent encrypted session and its own safety code. Each message is encrypted separately for each recipient, so no one — not even another member — can read a message that wasn't meant for them. Verify each peer's safety code separately.
  • Authenticated handshake. A ZRTP-style commit-reveal step (with explicit key confirmation) stops a relay from secretly sitting in the middle and grinding keys.
  • Uniform, padded traffic. Every message on the channel — typing notices, read receipts, deletions, call signaling, file chunks — is sealed in an encrypted envelope padded to fixed size buckets, so even someone who could break the transport sees only same-sized ciphertext blobs, not what kind of message you sent or how long it was.
  • Cover traffic (optional). Turn on 🕶️ Cover traffic and each connection sends a steady stream of decoy packets — indistinguishable from real ones — whether or not you're typing. An observer watching the encrypted channel (including the relay, in "max anonymity" mode) then can't tell when a real message goes out, or whether the conversation is active at all. It costs a little bandwidth; leave it off if you only care about content secrecy.
  • Forward secrecy. The session re-keys with fresh ECDH every ~10 minutes and destroys old keys, so a device seized later cannot decrypt earlier messages.
  • Zero-knowledge login (SRP-6a). Your password is turned into a verifier in your browser. It never reaches the server — or Cloudflare. Before that, it is stretched with PBKDF2-SHA256 (600,000 iterations), so even if the server's verifier store leaked, offline password cracking would be hundreds of thousands of times slower.
  • Self-destruct. Messages can carry a TTL and/or burn-after-reading; deletion is bilateral and nothing is stored on the server.

⚠️ Verify your safety code

When a chat becomes encrypted, both sides see a 6-emoji safety code. Read it aloud to your peer (in person or on a call you trust). If the codes match, no one is intercepting. If they differ, stop — the line is compromised. This is the one step only you can do.

For a stronger check, tap 📷 QR next to the code: scanning your peer's screen compares the full 128-bit verification token automatically — a man-in-the-middle has no realistic chance of surviving that comparison.

⚠️ The hardest problem: trusting the code you're served

This is the honest weak point of every end-to-end-encrypted website, Dead Drop included. The encryption runs in JavaScript that your browser downloads from this server on every visit. A server that is compromised — or whose operator is coerced — could serve a subtly modified script that copies your keys or messages before encrypting them. No amount of client-side cryptography can rule this out, because the attacker would control that very cryptography. Unlike a native app installed once and updated through a signed, reviewed channel, a website re-establishes this trust with you on each load.

What Dead Drop does to shrink that trust:

  • The whole client is open source, and every served file is hashed into a manifest (/SHA256SUMS) committed to the public repository. The Verify the code page re-hashes what you received and checks it against that manifest — and shows you how to compare it against GitHub, a source this server can't fake.
  • A strict Content-Security-Policy blocks any inline or third-party script, so injected code can't run — though this does not, by itself, stop a malicious first-party server.
  • Loading over the Tor onion (below) removes Cloudflare from the delivery path, so a TLS-terminating middlebox can't tamper with the code.

The real ceiling: if your adversary is the operator itself, a website cannot fully win — for that threat model you want a pinned browser extension or a native client. We'd rather say so than pretend otherwise.

What the server can and cannot see

  • ✗ Cannot read your messages, files, or call audio/video (end-to-end encrypted).
  • ✗ Cannot see your password (SRP — it never leaves your device).
  • ✓ Can see connection metadata: that two peers shared a room code, and (unless you use “Max anonymity”) their IP addresses during setup.
  • Cloudflare terminates TLS in front of the site, so it can see request metadata and signalling. It cannot see message content (that goes peer-to-peer) or your password (SRP). To avoid it entirely, use the Tor address below.

Hide your IP from your peer

Enable 🛡️ Max anonymity on the home screen to relay the connection through the server (self-hosted TURN). Your peer then never learns your IP, and vice-versa — the relay only ever sees encrypted DTLS, never content.

Duress / decoy password

In account settings (⚙️) you can set an optional duress password. Entering it logs you into a normal-looking decoy session instead of your real one. Because Dead Drop stores nothing between sessions, the practical value is mainly that you can hand over a working password under coercion without revealing your real one — the verifier check is done so the server can’t tell, from the request, whether a duress password even exists. Nothing in the API responses labels a decoy session, and a decoy session cannot touch the real credentials: changing the password from inside it changes only the password the coercer already knows. It is not a substitute for the panic button (💣) or for simply not opening the app under duress.

What this does NOT protect against

  • A compromised device (malware, keylogger, someone reading over your shoulder). Encryption can’t help if your screen is already visible.
  • Your peer screenshotting or saving what you send. Burn/TTL are cooperative, not enforced on a malicious peer.
  • Skipping the safety-code check — without it, end-to-end encryption can’t rule out a man-in-the-middle.
  • A compromised or coerced server serving backdoored code — the fundamental limit of any E2E website (see above). Use Verify the code, the onion, and ultimately a native client for the strongest guarantees.
  • Traffic analysis at a global scale (who talks to whom, when). Tor + Max-anonymity + cover traffic help, but nothing is magic.

Transparency

No accounts beyond a handle, no email, no message storage, no third-party analytics, no third-party STUN/TURN. Security headers and CSP are strict and same-origin only. The client is open source and the served bundle is verifiable — see Verify the code.
