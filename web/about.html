SECURITY & PRIVACY

Honest threat model. What this protects, and — just as important — what it does not.

How a conversation is protected

  • End-to-end encryption, post-quantum hybrid. Messages, files and calls travel directly between the two browsers over a WebRTC data channel. They are encrypted with AES-256-GCM using a key agreed by ECDH (P-256) + ML-KEM-768 (FIPS 203) → HKDF-SHA256 — an attacker recording traffic today cannot decrypt it even with a future quantum computer, because breaking the session requires breaking both primitives. The server only relays connection setup — it never sees keys or content.
  • Authenticated handshake. A ZRTP-style commit-reveal step (with explicit key confirmation) stops a relay from secretly sitting in the middle and grinding keys.
  • Uniform, padded traffic. Every message on the channel — typing notices, read receipts, deletions, call signaling, file chunks — is sealed in an encrypted envelope padded to fixed size buckets, so even someone who could break the transport sees only same-sized ciphertext blobs, not what kind of message you sent or how long it was.
  • Forward secrecy. The session re-keys with fresh ECDH every ~10 minutes and destroys old keys, so a device seized later cannot decrypt earlier messages.
  • Zero-knowledge login (SRP-6a). Your password is turned into a verifier in your browser. It never reaches the server — or Cloudflare. Before that, it is stretched with PBKDF2-SHA256 (600,000 iterations), so even if the server's verifier store leaked, offline password cracking would be hundreds of thousands of times slower.
  • Self-destruct. Messages can carry a TTL and/or burn-after-reading; deletion is bilateral and nothing is stored on the server.

⚠️ Verify your safety code

When a chat becomes encrypted, both sides see a 6-emoji safety code. Read it aloud to your peer (in person or on a call you trust). If the codes match, no one is intercepting. If they differ, stop — the line is compromised. This is the one step only you can do.

For a stronger check, tap 📷 QR next to the code: scanning your peer's screen compares the full 128-bit verification token automatically — a man-in-the-middle has no realistic chance of surviving that comparison.

What the server can and cannot see

  • ✗ Cannot read your messages, files, or call audio/video (end-to-end encrypted).
  • ✗ Cannot see your password (SRP — it never leaves your device).
  • ✓ Can see connection metadata: that two peers shared a room code, and (unless you use “Max anonymity”) their IP addresses during setup.
  • Cloudflare terminates TLS in front of the site, so it can see request metadata and signalling. It cannot see message content (that goes peer-to-peer) or your password (SRP). To avoid it entirely, use the Tor address below.

Duress / decoy password

In account settings (⚙️) you can set an optional duress password. Entering it logs you into a normal-looking decoy session instead of your real one. Because Dead Drop stores nothing between sessions, the practical value is mainly that you can hand over a working password under coercion without revealing your real one — the verifier check is done so the server can’t tell, from the request, whether a duress password even exists. Nothing in the API responses labels a decoy session, and a decoy session cannot touch the real credentials: changing the password from inside it changes only the password the coercer already knows. It is not a substitute for the panic button (💣) or for simply not opening the app under duress.

What this does NOT protect against

  • A compromised device (malware, keylogger, someone reading over your shoulder). Encryption can’t help if your screen is already visible.
  • Your peer screenshotting or saving what you send. Burn/TTL are cooperative, not enforced on a malicious peer.
  • Skipping the safety-code check — without it, end-to-end encryption can’t rule out a man-in-the-middle.
  • Traffic analysis at a global scale (who talks to whom, when). Tor + Max-anonymity help, but nothing is magic.

Transparency

No accounts beyond a handle, no email, no message storage, no third-party analytics, no third-party STUN/TURN. Security headers and CSP are strict and same-origin only.
