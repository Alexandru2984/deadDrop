SECURITY & PRIVACY

A precise threat model: what is encrypted, what metadata remains, and which promises a website cannot make.

Before you trust a conversation

  • Use uncompromised devices and browsers that received the intended client code.
  • Compare every peer's safety code over a separate trusted channel, then have both sides confirm it. Messaging, files, and calls stay locked until mutual confirmation.
  • Treat the 6 emoji as a 36-bit manual check. For a higher-confidence in-person check, scan the full 128-bit QR token.
  • If codes differ or the handshake fails, stop. A matching code strongly authenticates this session under the protocol assumptions; it does not mean nobody can observe or record the ciphertext and metadata.

What is end-to-end encrypted

  • Messages, files, and app controls. Pairwise protocol v4 combines ephemeral P-256 ECDH and ML-KEM-768, derives direction- and context-specific keys with HKDF-SHA256, and seals data with AES-256-GCM. The transcript, role, epoch, and content class are authenticated; replays are rejected.
  • Groups are pairwise meshes. A room holds at most six people and has no group key. Your browser creates a separate handshake, safety code, ratchet, and ciphertext for each recipient. Verify each row independently.
  • Calls use WebRTC DTLS-SRTP. Media is not wrapped in the app's AES envelope. Instead, the exact DTLS certificate fingerprint set is confirmed over the verified encrypted session before a 1:1 call is enabled.
  • Periodic key evolution. Fresh ECDH is mixed in about every ten minutes. The current and two prior epochs remain for in-flight data. This offers limited forward-secrecy/key-evolution properties, not a formally verified Double Ratchet guarantee; a browser cannot prove that dropped key objects were physically erased from RAM.
  • Hybrid/PQ scope. ML-KEM is intended to protect recorded traffic if its security and implementation hold even when P-256 is no longer sufficient. “Post-quantum” is a design goal, not a guarantee against future cryptanalysis, endpoint compromise, or implementation bugs.

Traffic shape is only partly hidden

Encrypted app envelopes use size buckets. This hides exact plaintext length within a bucket and makes some short control events resemble short messages. It does not hide timing, packet count, bucket changes, large files, call traffic, or total volume. Optional cover traffic adds one randomized short decoy roughly every 4–16 seconds; it is not constant-rate shaping and cannot make activity invisible to a capable observer.

What the service and network can see

  • Content: with the intended client, uncompromised endpoints, and mutually verified safety codes, the signaling server/TURN relay receives ciphertext rather than message, file, or call plaintext.
  • Account and session metadata: the Go server can associate a handle/session and source IP with a room code, peer ID, other room members, connection times, and the SDP/ICE signaling it relays. These values are kept in memory for active sessions but are not written to the app log.
  • Network metadata: nginx, Cloudflare, journald, coturn, the VPS host, and upstream networks may record IP addresses, paths, timing, sizes, or traffic volume. The application's generic logs are not the only logs in the system.
  • Relay-only mode hides each endpoint's IP from the other peer when TURN succeeds. The VPS/TURN operator still sees both endpoint IPs and timing. This is IP privacy from the peer, not anonymity.
  • Cloudflare terminates clearnet TLS and can see/modify page, API, cookie, and WebSocket signaling traffic. It normally does not carry the P2P data channel. The onion route removes Cloudflare from page/API/signaling delivery, but WebRTC/TURN follows a separate network path.

Storage, TTL, burn, and panic

  • The server persists handles, password verifiers/KDF labels, optional duress verifiers, invites, and an anti-enumeration secret. It does not persist chat rooms, messages, files, or calls.
  • TTL, burn-after-reading, and bilateral delete are cooperative browser behavior. A peer can screenshot, save, instrument, or modify their client; downloaded files and OS/browser forensic traces can survive.
  • The panic button clears this tab's in-memory state, closes connections, and attempts logout. It cannot wipe another device, infrastructure logs, crash dumps, swap, extensions, or data already copied.

Authentication and duress

New and upgraded accounts use SRP-6a. The password is not sent during a normal SRP login; the server stores a verifier, which still permits offline dictionary guesses if stolen. PBKDF2-SHA256 (currently 600,000 iterations) raises that cost but does not rescue a weak password. A legacy bcrypt account sends its password once to the Go origin—through Cloudflare on clearnet—then upgrades to SRP.

The optional duress password opens a normal-looking decoy session and API responses do not label it to the browser. The server necessarily knows which credential succeeded. A determined coercer, operator, device compromise, or forensic comparison can defeat the illusion; this is not cryptographically deniable authentication.

Trusting the code delivered to your browser

This is the fundamental limit of browser E2EE. A compromised/coerced server or TLS-terminating provider can send JavaScript that copies plaintext or keys before encryption. CSP, SRI, an embedded bundle, and /SHA256SUMS reduce accidental and some supply-chain changes, but a malicious first-party response can alter the page, script, manifest, and in-page verifier together.

Verify the code explains how to compare the manifest through an independent channel. That still cannot prove bytes already executing or detect every targeted response. A separately installed, signed/pinned client is required when the server itself is in the threat model.

Other non-goals and residual risk

  • Compromised endpoints, malicious peers, shoulder surfing, screen capture, and keyloggers.
  • Global traffic analysis or hiding that the service was contacted.
  • Account recovery: there is no email or recovery channel.
  • Formal assurance: this custom protocol has automated adversarial tests, but no independent professional cryptographic audit.
